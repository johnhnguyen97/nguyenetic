## Outline

1. **The line-height trap.** Western type defaults (1.4–1.5) crowd kanji.
   Japanese pages typically run 1.7–2.0. Show the visual difference with a
   side-by-side mockup of `日本語のUI設計` at `line-height: 1.4` vs `1.8`.
2. **Letter-spacing is meaningful.** `letter-spacing: 0.05em` reads as
   intentional spacing in Latin, but on a string like `お問い合わせ` the same
   value can break the perceived word boundary.
3. **Number formatting.** When does `1,000` vs `1000` matter? `Intl.NumberFormat`
   in `ja-JP` locale, plus the Japanese yen symbol (`¥` vs `円`) — when each
   convention applies.
4. **Form input modes.** `inputmode="numeric"` is not enough — for postal codes
   you also want the IME to switch to halfwidth. `<input type="text"
   inputmode="numeric" pattern="\d{3}-\d{4}">` is the magic incantation.
5. **Encoding traps that still bite in 2026.** Mojibake from bad legacy
   integrations, EUC-JP edge cases when consuming RSS feeds from older
   Japanese tech blogs, and why everything new should be UTF-8 with
   `<meta charset>` set early.
6. **Vertical text (`writing-mode: vertical-rl`).** Niche but useful for
   editorial designs and tategaki contexts.

## A glyph-fallback test

This post intentionally contains kanji so you can confirm the body font stack
falls back gracefully on every platform. The default `.prose-blog` rule lists
`Hiragino Sans → Yu Gothic UI → Noto Sans JP` after Inter; if a glyph isn't in
Inter, the browser walks the chain and renders `日本語のUI設計` correctly without
tofu boxes.

```ts
// Programmatic check: Intl.NumberFormat handles the locale split.
const yen = new Intl.NumberFormat("ja-JP", {
  style: "currency",
  currency: "JPY",
}).format(1234567);
// → "¥1,234,567"
```
